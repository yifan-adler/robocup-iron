# 2026 校赛 17 天计划：全员跑通优先

时间范围：2026-08-25 至 2026-09-10。

## 当前原则

- 暂不按专业或猜测分配角色。
- 前期四个人做同一套 onboarding，每个人都能启动官方平台和 Iron 四模式。
- 收齐技能问询和小任务实测后，再确定负责人、备份负责人和出题配额。
- 在获得可重复分数基线前，不做高风险策略重写。
- 每个关键流程至少两人掌握，比赛现场不能依赖唯一一台电脑或唯一一个人。

## 全员共同门槛

每个人必须完成：

1. 安装并验证 Docker/Compose；
2. 构建 Ubuntu 18.04 镜像；
3. 校验并解压官方平台；
4. 构建、运行官方 example；
5. 构建 Iron；
6. 跑完 Stage1 IT、Stage1 NT、Stage2 IT、Stage2 NT；
7. 找到 server/client/summary 日志；
8. 读懂一个 XML 的 env、instr、nl；
9. 根据一条失败日志判断故障层；
10. 填写 onboarding 记录和技能问询。

## 日程

### 8/25：仓库和规则

- 初始化 Git、整理归档、冻结候选基线和 SHA256。
- 阅读 README、环境指南和规则差异。
- 向校赛负责人确认出题数量、平台版本、模式和截止时间。

验收：所有人知道仓库入口、基线身份和规则中三项高风险处罚。

### 8/26–8/27：全员环境搭建

- Ubuntu 22.04 安装 Docker Engine；Windows 安装 WSL2 + Docker Desktop。
- 四人分别运行 `scripts/doctor.sh`、`docker compose build`。
- 记录宿主差异和安装问题，解决方法写入 onboarding 文档。

验收：四台机器都能进入统一容器并看到相同的目标平台路径。

### 8/28：官方平台基线

- 全员执行 bootstrap、build official、Stage1 IT official smoke。
- 失败只排查平台层，不修改 Iron。

验收：至少三台机器当天成功；剩余机器必须定位到明确阻塞层。

### 8/29：Iron 四模式

- 全员构建 Iron 并运行 smoke manifest。
- 收集逐题退出码、原始分、动作数和耗时。
- 连续执行三次，观察确定性和挂死。

验收：四人都能独立重跑并解释四种参数。

### 8/30：能力问询与后续分工输入

- 每人填写 `team-skill-survey.md`。
- 共同完成三个小任务：解释一个 XML、定位一个失败、画出 `main → Init → Run → Plan`。
- 只收集证据，不按专业先入为主。

验收：形成四份技能画像；下一次同步后再决定角色和个人配额。

### 8/31：题库工具与共同试题

- 全员学习 2025 出题指南和 2026 新限制。
- 每人试写 1 道 Stage1、1 道 Stage2，用校验器互审。
- 确认题目 manifest、作者/复核者和命名规范。

验收：8 道学习题完成自动校验和人工复核；不一定进入正式题库。

### 9/1–9/3：并行出题与基线诊断

- 根据 8/30 技能画像分配正式模块与出题配额；本文档此处不预设个人名字。
- 目标是每阶段累计 32 道候选题，具体个人配额在同步技能后补充。
- 同时用题目暴露解析、状态、调度、动作和超时问题，建立失败分类。

验收：每天新增题当天校验、当天由非作者复核，不把审题推到最后。

### 9/4：题库候选冻结

- 全量自动校验、官方平台运行和人工语义审查。
- 每阶段选 30 题，另留 2 题备用；若校赛确认只需总计 30 题，则调整提交集合但保留内部回归题。
- 对每题记录题型、作者、复核者、Stage、IT/NT、预期考点和实际分数。

验收：零格式错误、零重复任务/约束、零缺失复核。

### 9/5–9/7：安全修复与 A/B

在基线稳定后按顺序进入公共任务池：

1. 任务排序保存元素地址后容器变化导致的悬空指针；
2. Open/Close 未初始化重试计数；
3. AskLoc/递归纠错的次数和超时上限；
4. multi-goto 的位置 ID/物体 ID 混用；未通过专项集前默认关闭；
5. 结构化动作/耗时统计和确定性排序。

每项独立提交、独立回归。出现新崩溃、超时或无法解释的分数下降立即回退。

验收：报告逐题差异，不以“代码更复杂”或“总分偶然更高”作为合并依据。

### 9/8：代码和题库冻结

- 清理 Git 状态，固定容器、参数、源码、题库和哈希。
- 完成全量回归并创建 `school-qualifier-2026-rc1`。
- 导出稳定提交包和上一版本回退包。

验收：冻结后只允许修复可复现的提交/运行阻塞，不再引入新策略。

### 9/9：干净机器彩排

- 选择一台未参与主要开发的队员电脑，从干净仓库执行 onboarding。
- 模拟提交解压、编译、四模式运行、单题卡死、强制跳题和版本回退。
- 核对代码/题目文件夹命名和现场操作清单。

验收：不依赖口头指导完成；备用包能够在限定时间恢复。

### 9/10：校赛/提交

- 只使用 9/8 冻结包。
- 现场记录平台版本、命令、模式、题号和异常时间点。
- 不在现场合并未经回归的代码。

## 角色分配触发条件

以下信息齐全后再分配：

- 四份技能问询；
- 四份 onboarding 记录；
- Linux/Docker、C++、CMake、Python/XML、测试、规则/现场的实测结果；
- 每人每天可投入时间和比赛当天可用性。

届时为每个领域设置主负责人和备份负责人，并再决定个人出题配额。当前阶段只维护公共任务池，不在本文档中写死人名或专业对应角色。

## 每日站会格式

每人只回答四项：

1. 昨天跑通了什么，证据路径是什么；
2. 当前阻塞在哪一层；
3. 今天要交付的最小可验收结果；
4. 是否需要另一人结对。

禁止使用“差不多能跑”“应该是环境问题”作为状态；必须给命令、退出码或日志片段。
